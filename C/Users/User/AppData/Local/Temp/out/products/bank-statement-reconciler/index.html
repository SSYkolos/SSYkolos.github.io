02

What it does

  1. Balance audit on every statement

    Opening + credits − debits = closing, to the cent (or the bank's own control totals for MT942 and camt.054). Each statement gets VERIFIED, DISCREPANCY with the exact difference, or UNVERIFIABLE.

  2. Missing and duplicate statements

    Statements are put in date order per account, whatever order the files arrive in. A gap in the balance chain or a statement sent twice is flagged.

  3. Real bank dialects

    German ?20 subfields, Dutch /EREF/ tags, Polish ~20 subfields, SEPA keywords, SWIFT envelopes, multi-statement files, camt batch bookings, reversals and pending entries.

  4. Counterparty extraction

    Name, IBAN, BIC, end-to-end ID, mandate ID, creditor ID, purpose, return reason, booking text and GVC, as separate fields.

  5. Whole archives in one call

    Send a ZIP of statements. A damaged or unrelated file inside it is reported as a warning; the rest is still processed.

  6. Idempotent imports

    Every transaction carries a stable SHA-256 hash, so importing the same statement again never creates duplicates in an ERP or ledger.

  7. MT940 to ISO 20022

    Export as camt.053.001.08 XML. The export is validated against the official ISO 20022 schema in the test suite, and balances are never invented.

  8. Exact money, correct dates

    Amounts are decimal strings in the currency's minor units, never floats. Booking dates across year-end and late SEPA returns are resolved against the statement window.

03

Specification

Inputs
SWIFT MT940 and MT942; ISO 20022 camt.052, camt.053, camt.054 (versions .02 – .08+); or a ZIP of any of these
Outputs
JSON · CSV (Excel-ready) · hledger · Beancount · camt.053.001.08 XML
Verdicts
VERIFIED · DISCREPANCY (with the exact difference) · UNVERIFIABLE
Encodings
UTF-8, Windows-1252 / Latin-1; for Hungarian, Polish, Czech and other Central European accounts Windows-1250 / ISO-8859-2 / DOS 852, picked automatically
Endpoints
POST /v1/reconcile (file upload) · POST /v1/reconcile/raw (JSON body, text or base64)
Limits
10 MB per request
Safety
In-memory processing, protection against XXE, billion-laughs and ZIP-bomb inputs, optional PII redaction
Engine
Deterministic, no AI or LLM. The same input always gives the same output.

05

How it was tested

  • 128 automated tests, 10 realistic bank sample files and fuzz tests.
  • Run against about 65 public sample files from real European banks, including camt.052/053/054 versions 1 to 8. Every complete file is read.
  • Amounts match an independent open-source MT940 parser on 34 of 34 comparable files. The one difference is that library’s sign error on reversals, confirmed by the bank’s own balances.
  • Every camt.053 export is valid against the official ISO 20022 schema.
  • The container build runs the full test suite and fails if a single test fails.

06

Known limits

What it does not do yet, so you can decide before you integrate.

  • Not supported yet: BAI2 (US), OFX/QFX, CODA (Belgium) and pain.001 (a payment order, not a statement). These get a clear UNSUPPORTED_FORMAT message.
  • Very old DOS-encoded (cp850) German files may still show wrong umlauts.
  • Free text such as “AUFTRAGGEBER: name street zip city” keeps the name inside the purpose field, because name and address cannot be separated reliably.
  • A camt.053 export needs a balance, so MT942 and camt.054 files (which have none) cannot be converted to it.

07

Privacy

Statements are processed in memory and never written to disk. With redaction switched on, IBANs, counterparty names and emails are masked in the response.
